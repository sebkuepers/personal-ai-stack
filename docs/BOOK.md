# Book — editing one's own manuscripts

The repo's second domain (next to [`CRM.md`](CRM.md)). It supports writing books in
[Scrivener](https://www.literatureandlatte.com/scrivener/): export the manuscript, distil the
author's narrative voice into a checkable profile, and edit on that basis.

Built for **"Immer wieder Rügen"** (memoir / travel narrative), but designed for several works
from the start.

> **A note on language.** Identifiers, module and workflow names, schema fields, config keys and
> this documentation are English. German stays where the *subject matter* is German: the agent
> instructions (they teach German orthography and style), the controlled vocabularies in
> `shared/book.json`, the eval cases, and everything the author reads — CLI output, Studio display
> names, the strings in the conversational workflow. The rule: **if it names something, it's
> English; if it says something, it's German where German is the material.**

---

## The one rule that carries everything

> **The domain is the capability. The work is the subject.**

Agents, workflows, skills and Makefile targets are called `book-*` and apply to **every** book.
Which one is meant is said by the parameter `work=<slug>`:

```bash
make book-sync work=immer-wieder-ruegen
make book-sync work=autobiographie
```

That is why the second book costs not a single new definition — only a configuration file.

**Slugs** are kebab-case, ASCII, lower-case; umlauts are transliterated (ä→ae, ö→oe, ü→ue, ß→ss).
"Immer wieder Rügen" becomes `immer-wieder-ruegen`, and the same slug holds everywhere: directory,
Scrivener file, work configuration, Mistral Library, working data.


The directory keeps its German name: it is the author's filing convention, not repo code, and the
path lives in the work configuration under `paths`.

**Why not in `~/Documents`:** iCloud Drive syncs there. A program writing into a live `.scriv`
package while a sync service watches it triggers the classic Scrivener corruption scenario — the
service creates conflict copies **inside** the package. Finished files (ZIPs, PDFs, exports) may
and should be synced. Scrivener auto-backups therefore deliberately stay under
`~/Documents/Scrivener-Backups/` (that path is a **global** Scrivener setting and must never point
into a work folder).

> **Work data is not in the repo.** This repo is public; the work configurations and voice profiles
> contain chapter plans, touchstones, publishing strategy and verbatim evidence quotes from
> unpublished manuscripts. What is shared is the **domain** — code, agents, docs — not the
> **work**. Exactly the same separation the naming convention rests on.
>
> Whoever clones the repo creates their own work configuration:
>
> ```bash
> cp shared/book/work.example.json shared/book/my-book.json
> # fill it in, then:
> make book-sync work=my-book
> ```

## The division of labour

> **Read and compute locally, orchestrate in Mistral.**

Everything deterministic — measuring metrics, typesetting the PDF, writing back — happens in
`bookcli` on one's own machine. The workflows take care of agent calls, retries, parallelism and
the execution history.

**An earlier version of this rule was stricter and has fallen:** "no workflow touches the
`.scriv`." The reason was that the worker was meant to run in the Cloudflare container, where
`~/Werk/…` does not exist. But the book worker runs locally — so the reason fell away, and with it
a restriction that had a real price: a conversational workflow that may not read the chapter list
itself needs it as a parameter, and then it cannot be started in Le Chat without preparation.

What remains is the separation that matters: **I/O lives in activities, never in the workflow
body.** The body is replayed on a retry; a file that changed in between would throw it off course.
An activity reads exactly once, and its result is in the event history afterwards. The reading
activities are collected in `book/local.py`.

Nothing is still written from inside a workflow.

The **worker** — the process that runs the workflow code — runs locally and connects outbound to
Mistral. Orchestration, history and timeline live in Mistral's cloud.

## Usage

Prerequisites: `cd workflows && uv sync`, a `.env` with `MISTRAL_API_KEY`, and a Scrivener project
under `~/Werk/buch/<slug>/`.

### 1. Export the manuscript

```bash
make book-sync work=immer-wieder-ruegen           # → export/manuskript.json + Markdown
make book-export work=immer-wieder-ruegen         # additionally into the Mistral Library
```

The export is rebuilt on **every** run and never maintained by hand. It walks the **binder**
(`.scrivx`), not `Files/Data/` — the latter also holds *research* and the *trash*, which are not
part of the manuscript.

### 2. Distil the voice profile

```bash
make start-worker                                   # leave it in its own terminal
make book-voiceprofile-trial                        # trial run: 6 sections, writes nothing
make book-voiceprofile work=immer-wieder-ruegen     # full run, stores the profile
```

The trial run first. It costs minutes instead of a quarter of an hour and shows immediately
whether the rules get concrete or writing-guide prose comes out.

### 3. Edit

The **conversational workflow** is the actual workplace: in Vibe Work via `+` → Workflows →
*Book · Editing (conversational)*. It needs no input and reads Scrivener **live** — a `book-sync`
beforehand is not necessary. Scrivener only has to have saved; it writes `content.rtf` after a
typing pause.

The same levels individually, in the terminal:

```bash
make book-copyedit section="Einführung Strand"        # level 1, headless
make book-content chapter="Voll zur Oma"              # level 3, a whole chapter
make book-overview                                    # structure, density, state
make book-apply work=immer-wieder-ruegen              # preview the write-back; apply=1 for real
```

### 4. Typeset

```bash
make book-pdf chapters=1-3 compare=1     # typeset and hold the page count against the reference
make book-pdf                            # the whole manuscript
```

Needs `typst` (`brew install typst`). The measurements live in `shared/book.json` under
`typeset.format` and are **measured** from the reference PDF: 170 × 245 mm, text width 126.8 mm,
inner 23.6 / outer 19.5, Palatino 10.9 pt. Achieved: 71 pages against the reference's 70.

`break_between` is deliberately a setting (`all` · `groups` · `none`): the reference has 15
separators across 37 possible section transitions, with no discernible rule. Section titles are
not typeset, so the boundaries are invisible — this could not be derived, only decided.

### 5. Verify

```bash
uv run ruff check src/workflows src/bookcli src/evalkit ../agents tests/
uv run pytest tests/ -q
uv run python -c "from entrypoints.worker import discover_workflows as d; print(len(d()))"
make archive-stale     # registrations in Studio that the repo no longer defines
```

The discovery check only imports — it does **not validate**. Whether the workflows run inside the
Temporal sandbox is shown by a real worker start alone.

## How the voice profile works

The trap: ask a model to "describe this author's voice" and you get *"warm, humorous, concrete
images"*. True, useless and above all **not violable** — a rule you cannot break cannot detect a
breach either.

Six mechanisms force substance:

1. **Measure before modelling.** `stylemetrics.py` computes sentence lengths, short-sentence share,
   paragraph lengths, dialogue share, nominal-style and passive rates, purely deterministically.
   "Short sentences" becomes "median 9 words, 25 % at most 5 words, longest in the book 55".

2. **Only the manuscript, nothing else.** The author's editing notes (`notes.rtf`) once flowed into
   the reduce step with **priority** — and promptly 9 of 10 rules came from them instead of from
   the text. That is not a voice profile: the notes say what the author corrected in individual
   places, not how he writes. They are out.

3. **Every rule describes what the author DOES — never a prohibition.** The compelling reason: the
   agent only sees the finished text. It contains no violations of a prohibition, so a prohibition
   cannot be evidenced. A run without this requirement returned 8 of 12 rules as prohibitions, and
   **every** piece of evidence showed a sentence that complies with the prohibition — circular and
   worthless. One of those rules read "avoids elliptical sentences"; elliptical sentences are this
   author's signature. What he does not do lives under `avoidances`, where no evidence is required.

4. **Evidence required, enforced in Python.** The reduce agent gets a **numbered sentence
   catalogue** from the map step and picks from it instead of retyping quotes. It used to do the
   latter and paraphrased while doing so: 10 of 12 rules failed the evidence check because their
   "verbatim" evidence did not appear in the manuscript that way. The resolver accepts number
   **or** wording — `strict: true` enforces enums but not numeric types, and the model writes
   sentences anyway. Whatever is not in the catalogue is dropped.

5. **At most twelve rules.** Nobody reads a profile with forty rules and no agent follows it.

6. **Hold the evidence against its rules.** Point 4 checks whether a piece of evidence *exists* in
   the manuscript — not whether it *demonstrates* the rule. Exactly that went wrong: "direct speech
   without an introduction" was evidenced with a sentence containing no direct speech at all,
   "short sentences (≤5 words)" with one of twelve. For the style agent that is worse than one rule
   fewer, because it learns from the evidence what the rule looks like. `book-profile-check` holds
   every rule against its first piece of evidence; whatever fails goes to `status="beobachtung"`
   and no longer reaches the style agent. Measured on the real profile: 7 of 10 clean.

The fields are named after their content: `evidence` (places where you can see the rule) and
`violation_example` (the same place as it would sound from someone else). An earlier version was
called `beweis` and `gegenbeispiel` — and held the opposite of what the names promised. The style
agent read from it that the author writes in officialese, and promptly suggested officialese. The
successor `so_geht_es` repeated the mistake in the other direction: its name promised the model
case and it held the violation. Hence the explicit name today.

The result is used twice: as versioned JSON (the source of truth) and, at **call time**, as a
context block for the style agent — deliberately not baked into its instructions, otherwise every
profile change would require re-syncing the agent and the two would drift apart.

## The agents

All in `agents/book-*.json`, all with an enforced `response_format.json_schema`.

| Agent | Role |
|---|---|
| `book-voice-sample` | Map — observes the voice on **one** section, every observation with verbatim evidence |
| `book-voice-profile` | Reduce — condenses all observations into at most twelve checkable rules |
| `book-copyedit` | Level 1: spelling, punctuation, grammar, tense, typography. Does not touch style |
| `book-style` | Level 2: makes the text **more like** the author, not smoother. Must cite a rule of the voice profile |
| `book-second-read` | Second pair of eyes over level 1: sees the same section as stage 1 plus its findings and reports what is missing and what is not a finding |
| `book-style-second-read` | Second pair of eyes over level 2: checks per suggestion whether it delivers what its rule promises — `holds`, `inverts_the_rule`, `no_violation`, `overreaches` |
| `book-content` | Level 3: checks a whole **chapter** against the author's rubric. Changes nothing, asks questions |
| `book-profile-check` | Holds every voice-profile rule against its evidence: does the sentence show what the rule claims? |

The JSON schemas are generated **from** the Pydantic models in `book/models.py`
(`agents/build_book_agents.py`), with `$defs` resolved. That way schema and model cannot drift
apart. The instructions live there as readable constants — in German, because the agents work on
German prose.

```bash
uv run --project workflows python agents/build_book_agents.py   # generate the definitions
cd workflows && make sync-agents-dry                            # validate without touching Studio
cd workflows && make sync-agents                                # play them into Studio
```

Afterwards record the new IDs in `shared/book.json` under `agents`.

**Important:** workflows *trigger* these agents through the conversations API. Going via
`Agent(id=…)` + `Runner.run` would **overwrite** the definition in Studio with the fields passed in
— that is the difference between using and breaking.

## Skills and prompts — for working *with* Mistral

Three things can be played from the repo into Studio, all following the same pattern (`--dry-run`
checks without touching Studio):

```bash
uv run --project workflows python agents/sync.py     # agents
uv run --project workflows python skills/sync.py     # skills
uv run --project workflows python prompts/sync.py    # prompts
```

That way everything is versioned in git **and** visible in the Studio UI.

### What skills and prompts *cannot* do — against first impressions

The interface suggests both ("teach agents reusable skills…", "…to give to models from apps, agents
or API calls"). Checked against the live API on 2026-09-23, with a control attempt:

| Endpoint | Control (invented field) | `prompt_id` / `prompt` / `prompts` | `skills` / `skill_ids` |
|---|---|---|---|
| `/v1/chat/completions` | 422 `extra_forbidden` | 422 `extra_forbidden` | — |
| `/v1/conversations` (base call: **200**) | 422 `extra_forbidden` | 422 `extra_forbidden` | — |
| `/v1/agents` | 422 `extra_forbidden` | 422 `extra_forbidden` | 422 `extra_forbidden` |

**The control attempt is the core of the test:** the API validates server-side with
`extra="forbid"` and rejects unknown fields instead of ignoring them. Only that makes a 422 on a
candidate field a proof rather than a guess. For `/v1/conversations` a base call was issued first,
which does return 200 — otherwise the subsequent 422 would be worthless.

In addition: `beta.prompts` offers only `create`, `get`, `list`, `delete`, `create_version`,
`get_version`, `list_versions`, `update_metadata` — pure CRUD with versioning, no `render` or
`apply`. And an agent's permitted tool types are `code_interpreter`, `connector`,
`document_library`, `function`, `image_generation`, `web_search`.

**It follows that:**

* **Skills** apply to Vibe Work, Vibe Code and projects — not to workflow agents. Which is why the
  style agent gets its voice profile rendered into the prompt at runtime.
* **Prompts** are a versioned text library for the chat, not a runtime indirection. The list in the
  UI describes *where you use the text*, not that the API resolves it. Agent instructions therefore
  belong on the agent.
* Should a prompt ever be needed programmatically: `get()` takes `alias` and `version` besides
  `prompt_id`. A stable alias plus evolving versions would be the clean route — but the text then
  has to be substituted into the request oneself.

### Work content stays out

A skill in Studio has to be self-contained — Vibe cannot reach local files. So that no work content
ends up in the public repo anyway, both syncs know a placeholder:

```markdown
<!-- einbetten: shared/book/immer-wieder-ruegen-voice.md -->
```

The content is substituted **at sync time**. Only the scaffold is in the repo; the full version
lands in Studio. The embedded files (`*-voice.md`, `*-context.md`) are produced by `make book-sync`
and `make book-voiceprofile` and are gitignored.

## Measure instead of guess

`evalkit/` is **domain-independent** and therefore sits next to `workflows/`, not inside it. Every
agent in the repo raises the same question: does it deliver the right thing, and how would one
notice a regression?

```bash
make book-eval-cases           # build test cases from the manuscript
make book-eval                 # compare all configurations
make book-eval only=small/none  # a single one
make eval agent=<name> cases=<path>    # any agent, any cases
```

A case has two lists, and the second is the more valuable one:

* **expected** — must be found. Yields the *hit rate*.
* **forbidden** — must not be reported. Yields the *trap rate*.

An agent that reports everything has a perfect hit rate and is worthless; one that reports nothing
falls into no trap and is equally worthless. Only both numbers together say something.

The traps are set automatically when generating (from the list of protected colloquialisms in
`shared/book.json`), the **expectations deliberately not**: which passage is a real error and which
is voice can only be decided by the author. Guessed expectations would be worse than none, because
they fake a measurement.

### Why that is worth more than the next filter

After the first real run the temptation was strong to add a deterministic filter for every
misbehaviour. That yields a collection of workarounds which says nothing about the next, still
unknown error. The measurement showed instead that the **choice of model** solved the problem:

| Configuration | Traps | Time/case | Tokens |
|---|---|---|---|
| **small/none** | **0/12** | **4.9s** | **5,599** |
| small/high | 0/12 | 13.7s | 13,955 |
| medium/none *(previously configured)* | 1/12 ✗ | 8.6s | 8,660 |
| medium/high | 0/12 | 48.0s | 6 timeouts |

Both models know `reasoning_effort` only as `none` or `high` — `low`/`medium` are rejected with
HTTP 400. At `high` the model easily burns 2,000 tokens before the actual answer starts; if
`max_tokens` is too tight, a truncated answer comes back that looks like a model failure but is a
budget failure.

**The filters stay anyway** — but only the ones that check *invariants*: paragraph index,
non-findings, uniqueness of the search text. Those are cheap, absolute checks without discretion.
Substantive judgements belong in the choice of model and in the second read, not in a word list.

### The four-eyes principle — and how I built it wrong first

Level 1 runs in two stages: `book-copyedit` finds, `book-second-read` reads against it. The second
agent gets **the same section** as the first, plus its list of findings, and answers two questions:

1. **Is something missing?** Is there an error in the text that is not in the list?
2. **Is what is there correct?** Is one of the reported findings not a finding?

It runs **always** — the empty finding list is precisely the case nobody else checks.

**Its predecessor was a judge that ran per finding and received only `search` and `replace`.** That
is, a snippet without the sentence it sits in. Two things it therefore could not do: judge whether
an error is really fixed, and notice that one is missing. The second was the graver defect — at
zero findings it never even started, and a missed error was invisible. A reviewer who sees only the
first reader's suggestions does not review that reader's work, only their word choice.

The mistake came from thinking along the write path ("what may go into the manuscript?" is a
question per suggestion) instead of from the four-eyes principle. Mistral's built-in judge, by the
way, gets it right: it rates an answer **in the context of its request**, so it sees the full trace.

```bash
make eval agent=book-second-read cases=shared/book/eval-second-read.json count_path="missed[]"
```

The seven cases are constructed and therefore live in the repo. They cover the four operating modes
— clean text with an empty list, error correctly found, error missed, finding invented — plus two
work-context cases and **anchoring**: the error is still in the text, but the first stage delivered
findings that do not fix it. Observed with `medium`: the second reader then considered the passage
handled. Being anchored by the first reader's list is the principle's real weakness.

### Two stages, two models — on purpose

| Stage | Model | Measured |
|---|---|---|
| `book-copyedit` | `mistral-medium-latest` | 21/21 hits, 6/63 traps, 1.0s, 2,420T |
| `book-second-read` | **`mistral-large-latest`** | **16/16 hits, 0/26 traps**, 3.2s, 1,878T |

`large` is no luxury here: it beats `medium` (10/12) and `zai-glm-5` (11/12, 2 traps, five times the
tokens) and is the only model immune to anchoring.

That the stages use **different** models is deliberate on top of that. The research on
*self-preference bias* is unambiguous: a judge from the same family as the generator rates its
output systematically too well and shares its blind spots. A judge from a **different provider** is
recommended — that is on the list as a long-term improvement; for now the distance between `medium`
and `large` suffices. Mistral's own docs say nothing about model choice for judges; their best
practices only concern the instructions (be specific, testability, edge cases).

Side finding: `magistral-medium` delivers practically identical numbers to `mistral-medium` —
Magistral now sits inside medium/small as `reasoning_effort` and is obsolete as a separate model.

### The feedback loop — built, measured, removed

The idea: rejected findings go back to the agent, which may withdraw, narrow or defend them with
reasons. **Measured, it did harm** — 0 findings without it, 6 nonsensical ones with. The agent took
"narrow it down" literally and reduced its suggestions into meaninglessness instead of withdrawing
them.

The decisive objection came from elsewhere, though: a loop only fires after a rejection. That it
ran at all meant something was already broken in round 1. I had been treating the symptom and never
separated it from the cause. With the second read there is no second round: what it discards is
discarded; what it finds is added.

**Why no `handoff`.** Mistral knows handoffs, but there the *agent* decides whether to hand off.
Right for a division of labour, wrong for a QA gate: no fixed order, no access to the intermediate
states. Control structure belongs in the deterministic part.

### The test that should have come first

Every constructed case contained a planted error. The real text is edited several times over and
mostly clean — the **most common** case in the work, and the last one I tested. It looked like
this:

| Run on `Einführung Strand` (6 paragraphs, 278 words) | Findings | of those usable |
|---|---|---|
| before | 2–3 per run, different every run | 0 |
| after | **0 · 0 · 0** | — |

Among them was `„auskramen, die" → „auskramen die"` — the removal of a **correct** comma before a
relative clause. The most dangerous kind of finding: looks like punctuation, breaks the text.

The cause sat in the brief, not in the model. An agent told to "find errors" will deliver something
on a clean text. Three additions to the prompt fixed it:

1. **Invert the expectation.** Right in the first paragraph: the text is usually already edited,
   the empty list is the most common correct result, and every finding costs the author review
   time.
2. **"Optional" is disqualifying.** If your own reasoning contains "optional", "better", "nicer",
   "stronger" — then it is taste, not an error. One finding in a real run had described itself as
   "optional, but typographically correct".
3. **The reasoning has to match the change.** If it says "has to be capitalised", the change has to
   be a capitalisation. If the two do not match, the model has talked itself into something.

Re-measured, so that it had not merely gone quiet:

| | |
|---|---|
| Error planted into the real section (comma before `dass` removed) | **3/3 found** |
| Eval with expectations | 19/21 instead of 21/21 — finds more cautiously |
| Trap rate | **3/63 instead of 6/63** |

The three real false findings now sit as cases `H`, `I` and `J` in `eval-second-read.json`.

### No chunking at paragraph level

Measured on a section of six paragraphs with a known error inventory:

| | Required finds | Traps | Calls | Time | Tokens |
|---|---|---|---|---|---|
| **whole section** | **4/4 · 4/4** | **0** | **1** | **3.0s** | **381** |
| paragraph by paragraph | 4/4 · 3/4 | 2× idle | 6 | 6.1s | 473 |

Equally good at finding, but every individual call has its own urge to deliver something. For level
2 the question stays open — rhythm and repetition span paragraphs.

What **neither** mode found: the same thing written differently in paragraphs 2 and 5. Consistency
across a section is checked by nobody so far.

### Level 2 — a description is not a prescription

The most expensive mistake of this project, because I produced it myself. When the voice profile
was switched from prohibitions to descriptions — correctly — the style agent read the description
as a prescription:

```
Profile:  "uses elliptical sentences for pace"
Agent:    turns complete sentences into ellipses

Profile:  "often leaves direct speech without a speech tag"
Agent:    removes all speech tags

Profile:  "uses colloquialisms"
Agent:    replaces a word with a more colloquial one
```

Seven suggestions on one section, nearly all of that kind. Healing one side had broken the other.

Two changes, both measured against `eval-style.json` (seven cases from real bad suggestions, with a
synthetic profile and synthetic text, hence in the repo):

1. **The prompt searches for deviations instead of opportunities to apply.** The test question per
   suggestion is: *does the passage, AS IT STANDS, sound like a different author?* Not: could it
   sound even more like him? Trap rate 62 % → 42 %.

2. **`book-style-second-read`** with four verdicts, named after the real failure kinds: `holds`,
   `inverts_the_rule`, `no_violation`, `overreaches`.

It deliberately does **not** ask whether something is missing — unlike level 1. A missed style lapse
costs nothing; an imposed suggestion costs the author his voice. That is not a symmetric trade, and
the check has to reflect it.

Across both stages: of ten suggestions five rightly failed, and the three about a genuine break of
voice stayed. Live on a real section: seven suggestions before, one after.

### Level 3 — the author's rubric as the yardstick

`book-content` checks a whole **chapter** against three yardsticks, in descending authority: the
chapter rubric from `shared/book/<slug>.json` (`proves`, `must_carry`, `need_not_carry`, register,
history budget), the work's two touchstones, and the exposé from `kontext/expose.md`.

The exposé comes last and is explicitly marked as **intent**: it describes the book as it is
offered to publishers, not as the manuscript is. Confuse the two and every deviation looks like an
error.

This level changes nothing — no `search`, no `replace`, nowhere in the schema. The answer to a
substantive problem is writing, not replacing.

**What there was to learn: what is mandatory belongs in the schema, not in the prose.**
`touchstones` and `carries` stayed empty twice — even after an explicit instruction in the prompt
and with a doubled token budget. The reason was a `default_factory=list` on the Pydantic field:
with it the field is not under `required`, and then the model omits it. Removing the default fixed
it immediately.

### Foreign models: GLM 5.3 measured, not believed

The published GLM benchmarks (Terminal Bench, SWE-Marathon, Toolathlon) show clear leads — but they
measure agentic tool use. Our task is structured output over German prose. So it was measured, on
2026-09-23, three runs per effort level:

| | Hits | Traps | Time | Tokens |
|---|---|---|---|---|
| **Copyedit** medium/none | **18/21** | 2/63 | **1.0 s** | **2,083** |
| glm-5-3/max | 17/21 | **0/63** | 6.4 s | 17,515 |
| **Second read** large/none | **30/30** | 1/51 | **2.4 s** | **3,847** |
| glm-5-3/max | 29/30 | 3/51 | 8.0 s | 37,471 |

The disqualifier is not quality — that sits close together — but that GLM returns **invalid JSON**
in roughly one call in 30, truncated or empty, even with a 12,000-token budget. In a chain that is
a failed workflow.

A side finding that nearly decided everything while comparing: with the original budget of 4,000
tokens, GLM answers broke off mid-JSON and counted as model failures. That looked like a quality
problem and was a budget problem. **Whoever compares models has to give them the same room.**

The reasoning levels are model-dependent: Mistral knows `none|high` (anything else HTTP 400), GLM
5.3 `low|high|max`. Selectable in `evalkit` via `--models model:level`.

## Setting up a new work

1. Put the project at `~/Werk/buch/<slug>/<slug>.scriv` (outside any synchronisation).
2. Create `shared/book/<slug>.json` — use `work.example.json` as the template.
3. `make book-sync work=<slug>` and check that chapters and sections are right.

If the outline differs, the `structure` block helps. Autobiography example: research sits in the
draft next to the manuscript there (*Personen*, *Orte*, *Unternehmen*), all with
`IncludeInCompile=Yes` — without narrowing, those folders would be counted as chapters:

```json
"structure": { "root": "Kapitel", "chapter_level": 0 }
```

## Safety when writing into the manuscript

Built as `make book-apply` (`bookcli/apply.py`). The rules hold for every write:

1. **Scrivener has to be closed.** Otherwise it overwrites everything at its next save — silent
   data loss. Checked with `lsof`.
2. **Full package copy** into `backup/` before the first write of a session.
3. **Fourfold anchor** per change: `(section_uuid, paragraph_index, paragraph_sha256, search)`.
   The hash is checked again immediately before writing; `search` has to occur **exactly once** in
   the paragraph. On a deviation it aborts and names the section. **No fuzzy matching, ever.**
4. **Preview is the default**, `--apply` writes.
5. After writing, the file is **decoded again and held against the expected text**; on a deviation
   the backup is restored and it aborts.
6. **No agent edits the `.scriv` directly** — writing goes exclusively through `make book-apply`.

One detail that cost a measurement: the hash is checked against the paragraph **as it stood at the
start of the run**, not against our own intermediate states. It is meant to detect *foreign*
changes (the author kept writing in Scrivener). Checked against the running state it fires on the
second change within the same paragraph — and several findings per paragraph are the normal case.
Measured: 9 of 15 decisions failed on exactly that, although the author had approved them together.

The RTF roundtrip is covered by tests: every `content.rtf` has to decode character-identically to
Apple's `textutil`, and encode→decode has to yield the identity for every paragraph
(`workflows/tests/test_scrivener_roundtrip.py`).

**Next**

- Decision log → refining the voice profile via the acceptance rate per rule
- Run the whole chain end to end on a real section, by the author rather than by a test

**Long-term improvements**

- **Second read via a foreign provider.** The research on *self-preference bias* explicitly
  recommends a reviewer from a different provider, not merely a different model of the same family.
  GLM 5.3 was measured against both evals on 2026-09-23 and loses — not on quality (which sits
  close together) but because it returns invalid JSON in roughly one call in 30. One point in its
  favour is noted: zero traps in the copyedit task, it is more cautious. Re-measure when the eval
  passages are larger or Z.ai improves JSON fidelity.
- **Consistency across a section.** The same thing written differently in paragraphs 2 and 5 is
  currently found by no stage. That is deterministically checkable (compare word forms, collect
  proper nouns) and needs no model.
- **Derive the section separator from the reference.** Currently a setting, because the typeset PDF
  shows no discernible rule. A page-by-page comparison with the binder might find it.

**Deliberately not built**

Studio judges (`client.beta.observability.*`) are unreachable on the Pro plan — the endpoints
answer with HTTP 404. The second read therefore runs as its own agent. A later switch would stay
small: Mistral's judge rates an answer in the context of its request, so like `book-second-read` it
gets the full context; the criteria live as versioned text in `agents/build_book_agents.py` and
would only need registering.

A **correctness judge** for level 1 and an **overall quality score** are also absent: letting a
second model judge German commas costs money and adds noise, and an overall score is
unfalsifiable.
